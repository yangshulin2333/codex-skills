# 连接验证与有条件恢复

用于 Attach 失败、界面报成功但没有实际输出，以及同一工具此前可用而本次失效的情况。正常连接不需要为了本参考主动结束游戏。先确认本次目标和证据，再选择适合失败阶段的动作；任何 AI 或人工操作者都可以执行。

## 1. 绑定一次新尝试

在仓库外保存 attemptId、带 UTC 偏移的开始时间、目标 PlaceId/UniverseId、Player PID/版本/文件身份、工具运行根及关键文件 hash、当前日志路径和 native 日志时区。使用实际进程和当前场景，不能把历史 PID 或安装目录里的版本当成本次会话。

保留之前的日志、诊断和失败状态；将旧 PID/旧成功记录标记为历史，解除其当前会话绑定，不删除它们。重启、传送、进程变化或断线后重新检查身份；重新诊断且目录已占用时，用 `prepare_capture.py` 绑定新的 run/capture/tools 目录，不能删掉旧目录或强行重跑旧诊断。原始快照继续保留。

发布页上的相同或最新版本只能证明发布信息。没有本次真实会话证据，不能据此宣布兼容、不可用或已经恢复。

## 2. 根据观察到的阶段处理

| 失败阶段 | 可观察的结果 | 下一步 |
|---|---|---|
| 工具启动/依赖 | 启动错误、依赖缺失、实际运行根与预期不同 | 核对完整相对目录、运行库、实际文件/hash和日志；先解决确证的问题 |
| 前置初始化/内部函数候选查找 | native 日志在内部指令/函数候选查找报错，尚未得到成功握手 | 保留完整阶段和时间，核对当前 Player/工具及实际错误；不能当作后置网络失败，也不能直接断言偏移过期 |
| Attach/后置本地握手 | 已进入 Attach 流程，却没有当前 PID 的成功 ping/握手 | 核对当前进程、日志、本地接口和工具状态；只对已确认原因采取最小措施 |
| 诊断执行 | UI 显示执行成功，但没有本次诊断文件或 Player 标记 | 视为未通过；核对实际目标客户端、workspace、脚本生成配置和现场状态，不继续导出 |
| 身份/时间窗不匹配 | token 来自旧文件、旧 PID、其他 Place 或本次开始前的日志 | 不能复用为当前成功；重新绑定新尝试并取得相应证据 |

有的工具会报告自己的模块存在性，这只能辅助定位诊断未执行的阶段；没有实际输出时，UI toast 不能替代执行证据。同一错误、相同输入和相同状态下重复点击不会增加证据。记录失败并保存可续做状态，取得新版本、状态、日志或其他有效新证据后再评估。

没有明确依据时，不改偏移/补丁字节、不恢复来历不明的旧缓存，也不关闭系统安全设置。无法从证据确定原因时，保持原因未确定。

## 3. 必要时尝试受控冷启动

这是针对状态/时序问题的恢复候选，不是所有任务的固定步骤，也不保证修复内部初始化错误。

1. 先保存本次日志、当前场景身份、失败阶段及已有捕获/partial。评估重启会失去的回合、位置和尚未保存内容。
2. 完全结束游戏会话前检查用户是否已授权该影响；已有明确许可可以复用，不重复询问。没有许可时说明会话会结束并取得确认。授权归档本身不自动代表可以随时结束游戏。
3. 有授权后完整退出 Xeno 和对应 Roblox 客户端，确认旧进程已结束。仅处理本次绑定的进程，不结束无关的 Studio 或其他任务。
4. 先正常重新进入目标游戏，等待加载完成；核对 PlaceId 和 UniverseId 均与本次目标一致。若被送回大厅或匹配到另一 Place，应先到正确场景，不能沿用旧身份。原回合已经结束时如实记录，不能声称恢复了原快照。
5. 在启动工具或发起 Attach 前，记录新 Player PID、attemptId 和 fresh UTC 起始时间。再启动已核验的 Xeno，另行记录工具进程与日志，Attach 后执行本次新诊断并核对下节三项证据。不要把 Xeno 自身的 PID 填成 Player PID。

此受控尝试仍失败时，保存实际错误和下一动作，不循环相同操作或继续导出。新证据出现后可以重新评估适合的恢复分支。

## 4. 导出前的三证据门禁

三项证据应来自同一次尝试、同一目标客户端，且在记录的开始时间之后：

- **native 成功握手**：当前 PID 对应的 Attach 成功记录，保留原日志及其时区。
- **文件写读与身份**：本次 `diagnostic.json` 与 `diagnostic-probe.txt` 的 token 相同，PlaceId/UniverseId 与目标相符，诊断确认已加载。生成脚本通过实际 readfile 回读验证写入。
- **Player 真实执行**：本次 Player 日志包含同一 token 的执行确认标记，其时间落在本次窗口。不是任意旧 print，也不是执行器自己的 UI 提示。

使用仓库内验收器核对已保存的证据。[连接参数工作表](../templates/connection-verification.example.json) 可复制到运行目录填写，但它不是 `--config` 输入。以下是 shell 参数示例；所有变量先绑定本机实际值，Python 命令替换为已确认的运行时。Windows PowerShell 使用相应调用语法。

**先确认输入归属，再做文件验收。** 由操作者或可信现场工具把当前 Player PID、进程启动时间、选中的客户端、该进程的日志来源和本次捕获目录关联起来，保存这份观察依据。验收器只在 native 日志筛选指定 PID，不能从诊断 JSON 或 Player 的 CreatorOutput 独立证明其 OS 进程归属。现有诊断 token 使用秒级时间；多个同场景客户端同秒诊断时可能相同，不能据此交叉拼接证据。输入归属未确认时，即便 `passed=true`，也必须保持连接门禁未通过，不执行导出。

```sh
"$PYTHON" -B scripts/capture/verify_connection.py \
  --capture "$CAPTURE_DIR" \
  --place-id "$PLACE_ID" \
  --universe-id "$UNIVERSE_ID" \
  --native-log "$NATIVE_LOG" \
  --native-log-utc-offset="$NATIVE_LOG_UTC_OFFSET" \
  --player-log "$PLAYER_LOG" \
  --pid "$PLAYER_PID" \
  --not-before "$ATTEMPT_STARTED_AT" \
  --output "$NEW_CONNECTION_REPORT"
```

`--capture` 指向本次诊断输出目录；`--pid` 是本次 Player PID；`--not-before` 使用带时区的 ISO 时间，如 UTC 的 `Z` 或实际偏移，不能使用不带时区的本地时间。`--native-log-utc-offset` 来自日志实际时区；不能因机器当前时区或 Player 使用 UTC 就猜 native 日志也是 UTC。该参数使用等号形式，例如 `--native-log-utc-offset=-04:00`，避免负偏移被参数解析器误认为另一选项。`--output` 是新的报告路径，不覆盖历史结果；也可省略此可选参数而保存标准输出。输入包含本机信息，应留在运行目录，不提交公开仓库。

验收失败就保留诊断、日志和失败报告，停止导出并更新交接。验收通过也只证明这些记录内容在时间、身份与 token 上能相互匹配。报告中的 `processInputOwnershipChecked=false`、`operationalGateChecked=false` 表示没有验证各输入的 OS 进程归属，也没有代替操作者判定完整连接门禁；**`liveConnectionChecked=false`** 表示没有检测此刻的进程活状态、网络连接或当前游戏身份。输入归属已确认、文件验收通过且现场会话未变，三者成立后才将连接门禁更新为通过。若已断开、重启或切换场景，原报告只能作为历史证据。

现场仍为该会话且门禁通过后，按 [采集顺序](../scripts/capture/README.md) 继续 `inventory.luau → run_export.luau → terrain_probe.luau`，等待每步实际完成。`terrain.enabled=false` 只关闭指定范围采集，当前原始归档验收仍需要小探针；它不代表全量地形。

## 5. 已观察到的恢复案例及限制

一次真实排障中，前一会话与后一会话的运行文件逐 SHA256 一致。前一阶段曾发生后置本地 ping 问题，后一失败阶段却是前置内部指令候选查找；UI 还曾显示执行成功，但客户端模块没有相应执行结果，也没有新诊断文件。

保存证据并在许可范围内完整退出两者，先让相同 Place/Universe 加载，再启动同版工具并 Attach 后，观察到新 PID 的 native ping、本次诊断写读文件和 Player 同 token 执行标记，连接门禁通过。

这支持状态或启动时序可能有关；该次操作同时改变多个状态，没有隔离具体原因。它没有证明缓存损坏，也没有证明偏移地址过期或已被修好，更不能推导为任何连接失败都应重启。实际项目仍需独立完成场景、资源、缺失清单和 ZIP 验收。
