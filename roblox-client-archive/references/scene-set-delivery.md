# 主场景与活动场景：分别采集、恢复源码、打包交付

本流程衔接[完整工作流](full-workflow.md)、[连接恢复](connection-recovery.md)、[可选处理](optional-processing.md)与[打包 CLI](package-cli.md)。它适用于任何能读写本地文件、执行命令并操作客户端的 AI 或人工执行者，不依赖某个模型。先完成完整工作流中的 Xeno 来源核验、安装和连接验证，再执行本页；“客户端已能显示”不等于已完整归档。

[场景组工作表](../templates/scene-set.example.json)用于计划、证据索引与交接，**不是任何 CLI 的 `--config`，也不属于 `workflow_config.py` 的配置 schema**。复制后填写实际观测值；未知项保持 `null`。第二个角色可引用独立详情工作表，也可复制第一个场景的完整字段逐项填写，不共享验证状态。不要把本文路径示例、状态或脱敏案例当作已执行结果。

## 1. 先确定场景角色和独立边界

为每个场景建立独立的 `sceneId`、`role`、`roleBasis`、`captureRunId` 和输出目录，例如 `scenes/main-scene/`、`scenes/event-scene/`。主场景、活动子场景、匹配内地图均可作为用户分类，`roleBasis` 记录为 `user_label`，并保存用户说明的引用。

分别观测 Place、Universe、版本、时间和客户端进程身份。允许两个角色使用同一 Place；`samePlaceAllowed` 不表示它们一定相同。仅当实际证据支持时才填写 `separateTechnicalPlaceClaimed=true`。同一 Place 内运行时切换的场景也应独立采集和打包，不能仅靠 Place ID 区分。分类不意味着自动删除共享对象或把活动模型全部过滤。

进入目标场景后等待正常加载。若启用流式加载，注明已实际加载的区域与未覆盖范围。未进入、未下发或仅存在服务端的内容不能由当前客户端快照证明已保存。

## 2. 每次重启、重连或传送都重新建立采集证据

绑定当前进程、运行批次、原生日志时间范围及其时区。按连接恢复流程取得新的 Attach 证据和唯一诊断标记，并确认诊断输出属于当前客户端。离线日志相关性检查不能代替进程归属与实时连接检查；界面成功提示也不能单独证明游戏内执行。

连接通过后，按库存 → 场景 → Terrain 的顺序采集。记录每一步的开始、完成标记、产物路径、大小和 SHA-256；只有开始标记不能算完成。导出期间尽量保持当前游戏会话，避免传送、重进或切换场景。

若中途断线或重进：

- 将该批次记为 `partial`，保留其已经完成的库存、下载和日志；不要给不完整场景补写完成状态。
- 新建运行批次，重新验证连接，再补做未完成的采集。将旧、新批次的具体输入分别绑定到后续步骤。
- 不把多批次输入描述为同一瞬间的原子快照。可继续使用已经验收的旧库存下载，但其 manifest 必须仍绑定旧库存哈希。

采集后独立解析 XML、核对身份和关键数量、审查已知引擎排除、包装映射及重大不明缺失。库存与场景采集时间不同，动态实例和 Studio 自动添加对象都可能影响数量，不能仅以数量相近声称逐实例完全一致。Terrain 局部探测为空也不能证明全世界为空。

## 3. 下载与补充资源，保留请求级来源

每轮下载保存库存路径和 SHA-256、manifest 路径和 SHA-256、执行记录、完整性报告以及失败索引。后续验证必须使用该轮实际绑定的库存，不能悄悄换成较新的根目录库存。

需要补充时，先形成“最新库存引用 ∪ 场景真实资源属性引用”，资源属性应由类型信息识别，不能无差别抓取脚本文本里的数字。再减去前轮 manifest **所有已处理的规范请求键**，包括失败请求。仅对新增键及下载器明确发现的依赖补充下载；若决定重试旧失败键，另记一次有理由的重试，不能伪装成新增引用。

历史归档可以复用，但要核对规范请求键、文件字节与 SHA-256，并保存原 manifest 和来源证明。统计必须区分：

- `verified_historical_reuse`：已验收的历史本地字节，不声称是当前网络返回内容。
- `current_public_http`：当前公开端点实际返回的字节与时间。
- `current_installed_content`：从已确认安装目录读取的本地内容。

保留 401、403、404、本地缺失、无效引用和格式识别警告，不绕过权限，不用空文件冒充下载成功。下载完整性或已声明依赖闭包通过，只证明已记录文件与引用处理符合检查，不能写成所有资源都成功。若场景仍引用远程 ID，应明确账号、网络或权限仍可能影响显示。

## 4. 严格离线恢复 Luau，并生成阅读副本

先保留原始字节码和索引，按字节码 SHA-256 去重。记录每条脚本的 referent、类、完整路径、原字节码哈希及转换状态；空文件、错误消息和不支持的序列化版本应如实分类。

反编译器与 Luau 解析/编译工具是外部依赖，本仓库不捆绑它们。执行前核验工具来源、许可证、版本及文件哈希，记录真实命令数组、工作目录、输入、输出、退出码及 stdout/stderr。优先使用工具实际支持的严格模式，禁止通过合成控制流来冒充成功；不能把某个本地工具的参数当作所有工具通用参数。

每份候选 Luau 必须再经独立解析和编译检查，通过后才记为可交付的近似恢复结果。失败、空输出、解析失败、编译失败都保留原字节码及诊断，不自动生成假源码。严格检查通过不证明语义等价，也不恢复原始变量名、注释或完整工程。

如需 Studio 内阅读，制作新的 `snapshot/scene_with_luau.rbxlx`，原始 `snapshot/scene.rbxlx` 保持不变。只按 **referent 与原字节码哈希同时匹配** 的成功记录替换对应 `ProtectedString.Source` 内部内容；不全局按名字替换，不改其他属性，失败记录保持原样。在副本中加入清楚的近似恢复标记后，再检查实际插入文本的语法和编译。

保留修改副本、可重构补丁、验证记录和可执行回滚。对相同检查输入实测基线、修改版和独立回滚副本，记录数量、标记、stdout/stderr、退出码与哈希。验证补丁能精确重构副本，回滚后哈希等于原始文件；原始文件始终未改。恢复或归档的游戏代码不会因这一验证自动执行。

本次成功运行中的批次恢复适配器、反编译批处理和 Source 事务脚本属于具体本地运行，并未在此声明为通用 CLI。换工具或换导出格式时，先审查输入索引、XML 形式、参数与输出契约，适配后再验证；不能发明不存在的命令或把旧报告当作新执行结果。

## 5. 冻结目录，验证相对路径启动入口

每个场景独立 staging，包含原始场景、可选 Luau 阅读副本、资源及转换索引、身份摘要、限制说明和证据。明确 `.rbxlx` 是 XML 场景，`.rbxl` 是实际原生二进制场景，不能通过改扩展名转换格式。打开原件和阅读副本的入口应指向相应的包内相对路径。

原生与 XML 场景均可使用打包器生成启动入口。下例显式选择已经存在并验证过的 XML 阅读副本；先从本机配置绑定两个路径变量，并确保输出父目录存在：

```powershell
python scripts/package_archive.py --source $archiveSourceRoot --output $packageZipPath --scene-relative-path "snapshot/scene_with_luau.rbxlx" --metadata-relative-path "archive-summary.json" --launcher-scene-relative-path "snapshot/scene_with_luau.rbxlx" --create-launcher
```

创建包时，`--launcher-scene-relative-path` 必须与 `--create-launcher` 一起使用，目标必须是已存在的 `.rbxl` 或 `.rbxlx`；重验带入口的包时，该参数可与 `--verify-existing` 一起核对原始选择，不再传 `--create-launcher`。已有原生场景可继续使用 `--native-scene-relative-path`，具体组合和限制以[打包 CLI](package-cli.md)为准。这些参数只选择打开目标，不执行格式转换、反编译或 Play。

打包前停止对 staging 的写入并确认无锁、临时件和未完成下载。不要让 Studio 直接打开最终 staging，以免产生锁或改写场景。将候选或最终 ZIP 完整解压到独立可丢弃目录，对清单、启动入口、场景哈希和路径进行检查，再实际打开入口。预览件的启动入口和目标场景应与交付件逐字节一致，不能用另一份场景的截图代替。

分别记录以下结果，不做状态推断：

1. `launcherCheckPassed`：清单和 Studio 路径检查通过。
2. `studioProcessStarted`：启动请求实际产生 Studio 进程或对应窗口。
3. `sceneLoaded`：目标场景已在 Studio 打开，必要时用只读方式核对名称、对象及 Source 标记。
4. `renderPreviewVerified`：实际看到相应场景，并记录远程资源错误或显示缺失。
5. `playTestPerformed`：另行记录是否真正执行 Play；Edit 预览不等于玩法验证。

若 Studio 停在登录界面，记录“进程启动、场景未验证加载”，由用户本人完成登录。无现场执行证据的状态保留 `null`。若要把预览报告放入最终包，先预览独立候选件，再生成新的冻结 staging 与最终 ZIP，并复核交付入口及场景与预览件的哈希相同；不得在打包时继续往源目录补写报告。

## 6. 分包验收和交接

每个场景一个 ZIP，输出在源目录之外。核对全部 ZIP 条目的路径集合、大小、SHA-256 与 CRC，以及打包前后源目录不变。保留外置验收 JSON；重验既有包应使用新的报告路径。包级哈希是完整性证据，不证明内容来源真实性或所有权。

更新第二个场景时，记录第一个已交付 ZIP 的操作前后哈希，确认没有覆盖或改变。交接同时提供场景角色、实际身份、批次关系、成功与失败数量、打开方式、工具依赖和各级验证结论。阅读副本能打开不能据此声称完整源码已恢复、服务端已保存、所有资源已显示或完全离线可玩。

## 脱敏实测案例：用于理解证据边界

以下是一次已完成运行的历史观测，不是默认值、当前在线状态或普遍成功率。两份包属于同一 Place，以用户指定的“主场景”和“活动子场景”分别归档；未声称活动对象已全部过滤。

| 项目 | 主场景 | 活动子场景 |
| --- | --- | --- |
| XML 实例数 | 157,348 | 161,218 |
| 字节码记录 | 2,066 | 2,067 |
| 严格恢复并检查通过的记录 | 2,058 | 2,059 |
| 对应独立 Luau 文件 | 1,907 | 1,906 |
| 失败记录保留 | 8 | 8 |
| Studio 实际预览 | Edit 加载并显示，未运行 Play | 只启动到登录界面，未验证场景加载 |

主场景一次采集因重连中断，保留已完成库存和下载；新批次重新确认连接并完成场景。补充下载单独绑定新库存及场景引用，两轮 manifest 各自保存。合计 8,769 个不同请求键，2,427 条成功，对应 2,386 个不同哈希文件；来源为 2,268 条历史复用、158 条当前公开 HTTP 和 1 条当前安装内容。其余权限、缺失及无效引用均保留，未声称所有资源已下载。

Source 阅读副本的实例和 Source 属性数量与基线一致，恢复标记由 0 → 2,058 → 0，回滚哈希恢复。主场景最终 ZIP 共 21,763 条目、288,031,801 字节；逐条尺寸、SHA-256、CRC、文件集合及源目录不变检查通过，活动包原有哈希保持不变。主场景实际显示仍有远程资源错误；全部结果只覆盖客户端可读取内容、近似源码和归档完整性。
