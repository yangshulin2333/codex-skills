# 客户端、入站与真实验收

## 1. 先把“节点”拆清楚

| 对象 | 意义 | 不能据此推断 |
|---|---|---|
| 3x-ui 面板 | 管理配置、账户、关联与统计 | 面板能打开，不表示代理可用 |
| Xray 核心 | 真正处理协议与流量 | 进程运行，不表示指定入站已加载 |
| 入站 inbound | 监听地址/端口、协议、传输、安全参数 | 已启用、客户端数量非零，不表示身份正确 |
| 客户端 client | 用户身份、凭据、配额、到期、关联 | 独立客户端不一定需要独立端口 |
| 节点链接/订阅 | 供终端客户端导入的配置 | 链接可解析，不表示服务器接受该身份 |

用户只说“给新人加节点”时，至少确定：是否**独立凭据与额度**、复用还是新增入站、流量/到期/重置规则、交付给谁及通过何种私密渠道。没有需求依据，不自动设无限额度或某个固定配额。

另一条线路复用原客户端时，先确认同一身份、共享流量及撤销影响；不要把默认“全选所有客户端”提交给新入站。新入站和新客户端是两种可分别创建、关联的对象。

## 2. 发现本机 API，不照搬旧版本

优先使用当前面板 UI，或已验证的该实例 API。认证方式、面板根路径、对象结构、请求方法和返回体都可能变化；先查看当前面板的 API 文档/Swagger/OpenAPI，并核对安装版本对应的官方源码/发布说明。

能力记录至少包括：读取入站、读取客户端、创建客户端、创建入站、关联/分离、启用/禁用、设置配额/到期、导出配置、读取有效运行状态。缺少能力时退回 UI 或操作者执行，不猜接口。

**已核对的版本差异示例，不是通用请求模板：**官方 v3.10.2 的客户端是独立实体，存在 `/panel/api/clients` API；入站更新不再通过请求中的 `settings.clients` 管理关联，启用状态也有独立操作。旧版可能使用内嵌客户端结构。读取到 `settings.clients` 不代表此字段可写，更不能绕过 API 直接修改数据库。详见 [官方来源](sources.md)。

请求 URL 必须由已验证的 `PANEL_URL` 和该实例文档的路径组合；不得重复/遗漏面板前缀。会话与 Cookie 存在私密上下文，不写入 manifest、命令行历史或公开日志。API 返回成功后再读取目标对象及**关联关系**验证；响应丢失先查重再决定重试。

## 3. 创建及关联顺序

1. 保存目标现状与既有节点基线（私密），建立适当的一致性恢复点；备份失败停止写入，除非取得本次风险确认。记录目标 ID，而不只看备注名；备注可以重复。
2. 查询拟用端口是否与既有监听冲突，核对 TCP/UDP、IPv4/IPv6、防火墙与协议需求。
3. 查明该版本应用客户端/关联变更是否热更新、是否重启核心或中断连接。用户要求不影响现有用户而此行为不明确或会断连时，先停止并确认维护窗口/风险；只改目标记录不能单独证明无影响。然后根据用户选择复用或创建入站；使用该版本支持的协议/传输/安全组合，生成独立安全参数，不复制其他用户的身份或私钥当默认值。
4. 独立用户：用面板/该版本支持的方式生成新身份，设置确认过的配额、到期、重置规则，只关联授权入站。
5. 复用用户：读取并确认现有身份，确认共享额度、链接泄露和撤销范围后，仅附加到目标入站。
6. 回读：客户端启用、有效关联、实际身份、配额单位、时区与到期、服务器加载状态。**零客户端**的用户认证入站尚不能交付。
7. 从同一已保存对象导出链接。核对导出主机/端口、协议、UUID/认证、flow、传输、SNI、指纹、公钥/short ID 等协议适用字段；不要把几个节点的参数拼在一起。
8. 将连接链接/二维码/订阅视为凭据，只向授权接收人私密交付。截图隐藏秘密。

原生/Docker、旧/新客户端模型使用同样的结果标准，但操作命令与 API 载荷不能通用。

## 4. REALITY 专项检查

- 发现服务器及客户端**实际核心版本**；核对客户端是否支持所选协议、flow、指纹与加密参数。
- 依据当前官方说明选择可用的目标与 SNI；验证服务器侧 DNS、路由、TLS、目标端口、系统时钟。不把任一公共站点或域名当永久可用默认值。
- 核对公私钥对应、客户端公钥、short ID 和 SNI 的一致性；不要把服务端私钥放进客户端链接。
- 不猜测空的 `minimum_client_version` 的含义，它可能触发核心版本自己的默认下限；读取该版本说明及实际日志。
- 旧核心不兼容时**优先升级客户端**。确实不能升级才提交有依据的兼容例外：目标入站、最低支持版本、风险、用户批准、到期/撤销条件。不要默认填完全放宽值，也不要把本例某次成功的版本写为通用常量。
- `received real certificate` 等日志并不能唯一证明版本问题；也要检查密钥、SNI/目标、端口、时钟、网络干扰及配置是否生效。降低版本门槛可能增加识别/封锁风险，不能静默操作。

## 5. 分层验收

| 层 | 操作与证据 | 失败/未验时怎么报告 |
|---|---|---|
| L1 配置 | 使用该实际核心的帮助确认校验命令；检查协议、客户端身份及关联 | 配置未通过；不继续写入运行态 |
| L2 服务 | 服务/容器健康、目标入站已加载、日志无该目标的配置错误 | 服务层未通过，不反复重启掩盖错误 |
| L3 监听与网络 | 服务器监听 + 外部到目标端口；分清 TCP/UDP 和云/主机防火墙 | 端口可达只证明连通，不证明认证 |
| L4 指定代理 | 隔离进程/临时本地监听，用导出身份发送真实 HTTPS 请求 | 保存 URL、时间、核心版本、stdout/stderr、退出码与预期响应 |
| L5 用户终端 | 接收人实际客户端导入并连接，核对活动节点与结果 | 未做就写“用户端尚未验收” |
| L6 回读与回归 | 确认目标流量/身份活动证据，既有配置差异与抽样旧节点回归 | 不能把一次新节点成功当所有节点正常 |
| L7 恢复 | 私密备份校验、隔离副本恢复；生产恢复需窗口和单独授权 | 区分“副本恢复通过”和“线上恢复通过” |

不依赖特定测试站点的请求示例（POSIX shell）：

```sh
: "${PROBE_PROXY:?临时指定代理地址}"
: "${PROBE_URL:?经确认的HTTPS验收URL}"
: "${PROBE_TIMEOUT:?已确认的秒数}"
curl --noproxy '' --proxy "$PROBE_PROXY" \
  --connect-timeout "$PROBE_TIMEOUT" --max-time "$PROBE_TIMEOUT" \
  --silent --show-error --output probe.body \
  --write-out 'HTTP_CODE=%{http_code}\n' "$PROBE_URL" \
  >probe.stdout 2>probe.stderr
probe_exit=$?
printf '%s\n' "$probe_exit" >probe.exit
```

这些命令需要在一个不使用 `set -e` 中断记录的测试 shell 中运行。Windows 用 `curl.exe` 和 PowerShell 的 `$LASTEXITCODE`、`$env:...`/本地变量适配，不逐字粘贴 POSIX 语法。代理应为隔离测试进程的 loopback 地址，必要时使用 `socks5h://` 让代理端解析 DNS。勿更改用户的全局代理或正在工作的核心配置。

成功要求：退出码为 0、状态在用户指定的预期集合中，且响应正文/标记符合测试契约。需要时核对服务出口、目标活动证据，并做不经该代理的对照，排除规则直连/旁路。`HTTP_CODE=000` 表示没有取得 HTTP 响应，不是服务端返回的状态码。不要使用 `-k` 把证书错误变成通过。

## 6. 失败与撤销

保留失败证据，每次只检验一个假设。创建后失败时先回读“哪些资源已经存在”，再决定修复还是撤销；只禁用/分离本次对象。共享客户端撤销可能影响多个入站，必须先检查引用。删除前确认可恢复性及操作者授权，不删除其他人的客户端，不无条件重试创建。
