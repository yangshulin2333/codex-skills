# 手机 Google 服务安装与修复

目标是让用户需要的 Google 服务实际可用，并留下可接手的状态记录。不要把“安装了几个 APK”当作成功。

本文件可由任何 AI 或人工执行者阅读，不依赖特定平台、插件、记忆系统或命令工具。有设备工具时实际执行；没有时给出与当前界面对应的人工步骤，并明确哪些结果仍需用户确认。

## 运行时发现，不预设设备事实

每次连接重新读取目标设备、系统构建、Android 兼容能力、API、ABI、当前用户、已有组件及权限。电脑路径、设备标识、安装包版本、备份目录与日期、界面坐标、活动组件名均从当前环境或可信资料取得。公开安装资源的口令按其可信说明取得；用户自己的加密备份密码只由用户在设备上输入，不读取、不保存。

技术文档中的 API、权限和错误名称是识别线索，不是要求所有设备都使用同一参数。不要从本 skill 推导出固定机型兼容表、固定安装包组合或固定日期。

## 先建立检查点

只推进尚未完成的阶段。每个检查点保留“观察结果、证据、下一动作”，使用 [运行记录模板](references/run-record-template.md)；不要写入账号、密码、验证码、令牌或完整个人备份内容。

| 检查点 | 通过条件 |
|---|---|
| 连接 | 已明确选定目标设备，连接授权有效 |
| 预检 | 系统能力、已有组件、冲突及可恢复的设置基线已确认 |
| 方案 | 当前设备符合所选方案的前提，用户目标与方案一致 |
| 前置条件 | 必需的系统支持、恢复步骤、激活及安装策略已完成 |
| 安装 | 所需包的身份、版本、签名及实际安装结果正确 |
| 权限 | 当前组件获得其运行所需的实际权限或兼容支持 |
| 使用 | 账号、商店加载、搜索、实际下载与安装通过验证 |
| 收尾 | 临时设置恢复、测试内容清理、结果与限制记录完整 |

## 1. 一次完成最小预检

若用户说“按上次的方法”，先读可访问的成功记录，提取依赖顺序和关键证据；将旧设备结论视为候选，不复制其设备参数。不要因只记得最后几个 APK 而漏掉前置步骤。

一次收集：

- 连接状态、实际型号、完整系统构建、Android API/ABI、当前用户，以及电量和安装空间是否足够。
- 系统是否能原生运行所需 Android 组件；已有服务、框架、商店、兼容层和助手的包身份、版本、签名与启停状态。
- 时间是否正确，手机实际能否访问当前登录或商店所需端点。浏览器访问成功只证明所访问端点可达。
- 用户已有账号和组件的数据影响范围；只记录是否存在，避免读取账号内容。
- 本次可能改变的设置原值，例如自动时间、时区和屏幕方向。

工具应在当前环境发现并复用，避免重复下载。使用 ADB 时，每个设备命令显式指定本次选定的设备；未授权、离线或目标不明时不发安装命令。不要为了重置单一连接而随意中断其他设备的会话。

可选的 [只读预检脚本](scripts/probe_android.py) 使用 Python 标准库。先用 `--help` 查看接口；`--list` 只枚举设备，正式预检必须提供 `--serial`，候选包通过重复的 `--package` 传入。它不安装、不授权、不验签，也不替代 UI、网络、空间和兼容性检查。没有 Python/ADB 时人工完成同样的观察即可。

## 2. 选定方案，再确定安装包

生成一张简短方案卡：**目标能力 → 当前设备依据 → 组件角色 → 必需前置条件 → 安装顺序 → 验收方法 → 数据影响**。

| 当前条件 | 处理方向 |
|---|---|
| 设备具备原生 GMS 支持，组件缺失、停用或损坏 | 按厂商与 Google 的当前支持方式补齐或修复 |
| 设备支持所需兼容机制，用户接受 microG | 使用适配当前系统的官方兼容组件，并分别验证服务兼容和商店权限 |
| 原生或兼容条件不满足 | 说明具体限制；只有用户接受时才改用容器等替代方案 |

“Google 三件套”是口语称呼，不等于每种方案都安装相同三个包。按组件角色和当前文档确定依赖；不要同时叠装冲突的官方服务、替代服务、商店占位包或容器。microG Companion 与官方 Play 商店的取舍应按 [microG 当前安装说明](https://github.com/microg/GmsCore/wiki/Installation) 核对。

某些 OEM 固件与商店组合可能需要额外的特权安装前置步骤；它可以与 microG 配合，但不是所有 microG 设备的要求。仅在证据支持时阅读 [旧式 OEM 恢复与特权安装](references/oem-legacy-recovery.md)。

对候选 APK 一次核验来源、包标识、版本、SDK/ABI、拆分包完整性、签名完整性和发布者身份。已验证缓存可以复用，但先比对哈希与来源记录；同一个未变化的文件无需在每次重试时重做完整核验。兼容性、安全修复与发布状态使用当前资料核对，不固定“最新版”或“某个旧版永远可用”。

## 3. 先完成依赖，再安装受影响组件

按方案卡检查前置条件，不把“已安装助手”“已打开管理员页面”“声明了权限”误记为完成。

**服务签名兼容与 Play 商店运行特权是两个独立检查点。** microG 自检通过，不代表官方 Play 商店获得所有所需权限。管理员已激活，也不自动证明另一个应用得到系统特权。

方案要求恢复助手数据时，核对的是恢复完成、管理员实际激活、助手进入预期工作页面、安装策略可用等结果。某些策略只影响之后的安装；策略生效后，按该方案对受影响包执行保留数据的同签名重装，再核对实际权限。不要因此重装所有组件或删除已登录的服务数据。

用户授权“最高权限”表示完成已选方案所需的权限步骤，不自动扩大为 root、解锁引导程序、刷机、关闭防护或授予无关权限。缺少的特权必须通过设备支持的机制取得，不能靠反复授予普通运行时权限替代。[Android 特权权限机制](https://source.android.com/docs/core/permissions/perms-allowlist)

按当前方案文档完成必要的重启、后台运行和电池优化配置，并核对结果；仅调整相关组件，不批量更改其他应用。重启后重新检查连接、解锁和当前状态，再继续账号与商店验证。

## 4. 顺序操作界面，集中处理人工节点

- 同一时刻只有一个界面操作者。自动操作期间请用户保持解锁；交给用户验证或登录时，暂停点击、切换应用和其他会遮挡该流程的操作。
- 每次操作前读取当前界面，优先使用文字、资源标识或可访问性节点。坐标从最新布局计算，不能沿用旧截图坐标。
- 操作后等到可观察的完成状态，再执行依赖动作。扫描中、安装中、二次风险确认、指纹验证和恢复完成是不同状态。
- 请求手机端操作时，一次说明当前任务需要的动作。USB 授权、指纹、锁屏密码和账号验证由用户在设备上完成，不索要秘密。
- 用户说完成后先查实际状态；已通过的授权不重复索取。等待时可做独立的只读核验，但不得继续操作正在由用户控制的页面。

不要用长期关闭安全功能解决普通安装确认。缺少明确前置条件时先诊断，不让用户反复重试登录或安装。

## 5. 按证据排错，避免无效循环

每次失败先保留最小相关证据，再采用“假设 → 一项针对性动作 → 结果核对”。相同条件和相同错误不重复执行相同动作。读取 [故障分流](references/diagnostics.md) 中对应的一项，不一次加载所有高级分支。

优先检查当前方案的依赖、实际授权和 UI 状态，再考虑更换版本或方案。签名冲突、系统不支持、来源无法核验、所需权限没有可用取得机制时，停止该安装分支并说明缺少什么。不要用批量卸载、清数据或更换账号掩盖未知原因。

范围内可逆修复继续执行；会影响已有数据、改变用户选定方案或需要额外系统改造时，先说明具体影响并取得相应授权。已有授权有效时不重复询问。此 skill 本身不提供操作授权。

## 6. 验收、恢复设置与交付

根据用户所需能力核对：组件状态 → 所需权限/兼容自检 → 用户完成账号登录 → 商店正常加载与搜索 → 实际下载安装。测试应用应免费、来源明确、适合当前系统，不订阅、不付费、不另建账号；打开测试应用确认可启动。仅移除本次明确新增的临时测试内容。

恢复本次临时改变的时间、时区、方向、连接转发或临时服务；完成、失败、退出或交接时都检查这一项。不要顺手重置用户原有设置，也不要未经判断移除仍影响后续更新的安装策略。

不能把商店可用等同于设备已获 Google 认证；支付、银行应用、推送与其他完整性要求仅在实际测试后报告。[Google 认证说明](https://support.google.com/googleplay/answer/7165974)

最终简要报告采用的方案、已验证的功能、未验证或仍受限之处，以及临时设置恢复情况。未通过的检查点如实保留，供下一位 AI 从该处接手。

## 持续维护

新设备的实际参数、包组合、哈希和成功证据写入独立运行记录，不写回通用正文。只有重复出现且证据清楚的机制性经验才更新 skill，并标注适用条件；失败尝试不升级成永久必做步骤。
